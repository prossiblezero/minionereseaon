## 一、任务与数据

<a id="q01"></a>
### 01｜用 90 秒介绍项目　P0

**面试官**：这个项目解决什么问题，你做了哪些工作？

**答**：

> MiniOneReason 研究生成式推荐中的训练信号和推理成本。基于官方 OneReason-0.8B，把用户多域行为转成商品 SID，先做直接与混合推理 LoRA SFT，再比较四种 RL 设置。
>
> 核心工作是处理精确命中奖励稀疏：用四段推理、每段八个答案的 N×K 采样，配合三级 SID 前缀奖励，并把共享推理的优势设为子答案优势的均值。奖励探针中，有差异的组从标准八采样的 3.12% 提高到 22.66%。
>
> 本地测试中，thinking Recall@32 从 mixed 的 2.233% 到 4.467%。固定权重做五次非思考采样，平均从 1.836% 到 3.474%。之后用有效性分解、预算路由和官方商品评测，继续检查收益来自哪里、花了多少成本。

**解析**：开场交代任务、核心机制和一个验证链即可。SFT、RL、预算依次回答“先学会什么、反馈够不够、收益值不值”。

**追问**：哪一项最能体现判断？可以从“增加 32 条完整采样收益有限，于是检查奖励覆盖”展开，接到第 15–19 题。

**依据**：[故事的口述稿](项目故事-MiniOneReason.md#十三面试时讲成一条研究经历)、[结果口径](实验结果与来源.md)。

<a id="q02"></a>
### 02｜生成式推荐怎样从输入得到商品　P0

**面试官**：输入输出是什么？为什么生成 SID？

**答**：输入是商品、广告、视频等多域行为历史，附带商品推荐请求。模型输出商品领域标记和三个离散编码 token，例如 `<|prod_begin|><s_a_12><s_b_34><s_c_56>`。SID 沿用官方预训练表示，三个码位都在 0–8191 范围内。生成后要检查格式、领域和完整 SID 是否存在于商品目录。

**解析**：训练前已有 SID 词表和预训练模型，本项目在这个表示上做后训练。它的作用是把候选预测写成自回归 token 生成。三个码位各自合法，不保证其组合对应目录中的商品；目录成员检查因此是独立一步。

模型可以生成目录中没有的组合，也可能生成同一个组合多次。生成预算、合法率和去重后的覆盖量各有不同含义，不能只看最后打印出了一个编码。

**追问**：前缀一样就代表同一类别吗？本实现把前缀相似当作奖励塑形的代理；项目没有人工验证每个一级码的类目含义。要证明语义一致，还需要商品元数据或编码分析。

**依据**：[tokenizer 检查](../model.py#L9)、[SID 解析](../data.py#L53)。

<a id="q03"></a>
### 03｜为什么配置五万条，实际训练只有 2,647 条　P0

**面试官**：训练数据怎么来的，为什么这么少？

**答**：50,000 是配置上限。公开 SFT 的 102 个分片共有 48,269 条，按最终答案筛商品领域后剩 3,988 条，再去除训练重复、目录外目标、裁剪后推理引用失配和超长答案，得到 2,647 条训练、385 条验证、403 条测试。实际数据量由这些规则决定。

**解析**：四类后续拒绝分别是 213、321、17、2 条，总计 553；3,988 − 553 = 3,435，正好等于三个集合的总量。程序按处理顺序记首个失败原因，因此拒绝表是互斥计数。

目录约有 1,030 万个不同商品 SID，训练样本规模很小。这会影响精确奖励覆盖，也解释了为什么需要测训练支持度，而不能只用“模型有没有收敛”判断数据是否够用。

**追问**：为什么不复制到五万条？复制增加训练次数，不增加独立用户历史或目标覆盖；需要更多优化预算时应通过 token 匹配或明确的 epoch 配置控制。

**依据**：[数据报告](../reports/data_report_main.json)、[prepare](../data.py#L165)。

<a id="q04"></a>
### 04｜训练与测试怎样分开　P0

**面试官**：直接随机划分不行吗？

**答**：项目按规范化后的输入历史分组。先去掉末尾任务请求和空白差异，计算 `group_id`，再对 `group_id + "42"` 做 SHA256、模 100，按 80/10/10 分配。相同历史始终在同一个集合，训练里的相同历史与目标重复记录再去重。

**解析**：按记录随机分会把相同历史分散到不同集合。分组解决的是这类输入重复；它不依赖目标选择集合，因此同一历史对应多个目标时仍在同一组。

公开输入缺少可核实的完整用户身份和时间戳，本次采用的是历史组留出。后续若拿到用户 ID 和时间，可补用户互斥与时间外推测试，回答更贴近上线的问题。

**追问**：验证和测试为什么还留重复？重复记录保留在同组，统计时按组重采样，避免把同源输入当成独立样本。test 为 403 条、314 个组。

**依据**：[split_for / normalize](../data.py#L83)、[配对比较组数](../reports/nk_prefix_vs_direct_42.json)。

<a id="q05"></a>
### 05｜怎样让目标信息不进入输入　P0

**面试官**：做历史选择时会不会用目标挑历史？

**答**：所有 prompt 和历史选择函数接收 `input_view()`，其中只保留 `sample_id`、`group_id`、`history`、`context_text`。目标 SID、教师推理和目标描述用于监督或评分，处在输入视图之外。测试会修改目标字段，检查输入选择和 prompt 是否保持一致。

**解析**：字段白名单让边界落在调用接口上。比如 balanced 可以按历史中的商品领域和一级 SID 分配预算，却拿不到“本题目标属于哪个一级码”。完整目录是独立商品表，也不把目标候选单独列给模型。

目标 SID 本来出现在历史中是另一回事：当前任务允许重复推荐，已有真实行为中的商品不应因为后来成为标签就被删掉。

**追问**：这是否排除了预训练污染？该接口防止当前数据管线把标签放进输入；预训练语料重叠需要另外核实。

**依据**：[input_view](../data.py#L88)、[目标变更测试](../tests/test_pipeline.py)。

<a id="q06"></a>
### 06｜为什么要检查 CoT 引用和答案长度　P1

**面试官**：裁剪历史以后，继续用原推理训练会怎样？

**答**：如果教师推理引用的历史已经被裁掉，模型看到的条件就不支持监督内容。项目检查 CoT 中引用的 SID：原始历史之外的引用要核查，属于历史却被当前裁剪移除的样本会过滤；监督答案超过 1,024 token 的样本也过滤，避免截断最终 SID。

**解析**：这里保证的是结构、可见引用和长度一致。例如原历史有 A、B、C，裁剪只留下 B、C，CoT 却根据 A 得出结论，这条监督会教模型在看不到 A 时提到 A。

引用匹配仍不检查自然语言里的每个事实。一个 SID 真的在历史中，围绕它编出的日期或搜索行为也可能缺少依据；第 38 题讨论这类问题。

**追问**：direct 为何也用这批样本？direct 和 mixed 使用公共有效 CoT 子集，可以先控制样本差异，比较监督形式。

**依据**：[prepare 的引用和长度过滤](../data.py#L165)、[training_records](../train.py#L12)。

<a id="q07"></a>
### 07｜千万级目录在训练与评测中分别做什么　P1

**面试官**：目录是每题候选集吗？为什么要全量读取？

**答**：目录是独立 Pid2Sid 商品映射中的全部商品 SID 集合，包含 10,295,563 个不同编码。它用于过滤无效训练目标、验证模型生成的候选，并给传统基线提供完整检索空间。模型输入只包含历史和任务请求。

**解析**：每题提供目标及若干负例会改变任务难度。这里生成模型自行输出 SID，评测检查是否属于全目录，再与监督目标比较。传统基线则对目录候选打分取 top-K，因而两类系统的候选产生方式要标明。

目录构建还核实了 2,080,061 个碰撞 SID。碰撞按不同 PID/SID 对计数，原始行重复另行排除。

**追问**：目录太大时怎么办？当前实现读取 SID 集合到内存；更大规模可以研究压缩索引或编码级成员检查，选择应以实际内存和查询开销为依据。

**依据**：[目录构建与碰撞审计](../data.py#L138)、[catalog_report](../reports/catalog_report.json)。

## 二、SFT 与公平对照

<a id="q08"></a>
### 08｜direct 与 mixed 的训练样本怎么构造　P0

**面试官**：两种 SFT 到底差在哪里？

**答**：每个基础样本展开两次。direct 两条都是直接生成 SID；mixed 一条直接生成，一条生成原始教师推理再接 SID。两边基础样本和展开后的 5,294 条训练记录相同，通过聊天模板控制是否进入思考模式。

**解析**：direct 的模式循环是 `(False, False)`，mixed 是 `(False, True)`。这样控制训练记录数量，但 mixed 轨迹更长，处理 token 和受监督 token 仍不同。项目因此另做第 10 题的 token 控制。

mixed SFT 训练的是两种条件下的行为：给定直接模式时尽快输出目标，给定思考模式时模仿推理及答案。它本身没有引入结果奖励筛选或在线探索。

**追问**：这是不是 RFT？这里的 mixed 是两种监督格式的 SFT。按生成结果筛选再训练的 RFT 属于另一训练流程，本次没有运行。

**依据**：[training_records](../train.py#L12)、[训练账本](../reports/training/main_mixed_42_complete.json)。

<a id="q09"></a>
### 09｜assistant-only loss 具体屏蔽哪些 token　P0

**面试官**：输入在前向里参与了计算，为什么说它不受监督？

**答**：输入当然参与前向，模型要根据历史预测答案。监督标签把 prompt 位置设为 `-100`，只在 assistant completion 上计算交叉熵；padding 也设为 `-100`。mixed 的推理正文、结束边界、商品 SID 和 EOS 都属于 completion。

**解析**：用掩码写成 `L = −Σ m_t log p(x_t | x_<t) / Σ m_t`。掩码为零的位置提供上下文，却不直接要求模型复现该位置的 token。Transformer 的梯度仍可以通过后续答案损失传播到输入相关计算。

标签对齐由 causal LM 的训练实现处理；手工计算 token log-prob 时则要注意第 t 个 logits 预测的是下一个 token，不能把位置错配。

**追问**：只监督最后四个 SID token 会怎样？那会把 mixed 的训练目标改成“把推理当上下文，最终只学答案”；需要独立实验比较，当前 mixed 也监督推理正文。

**依据**：[标签构造](../train.py#L12)、[DataCollator 配置](../train.py#L29)。

<a id="q10"></a>
### 10｜token 匹配为什么还要改学习率调度　P0

**面试官**：让 direct 多训几轮不就公平了吗？

**答**：项目用 selected mixed 检查点实际处理过的 3,958,467 token 作为 direct 的预算，达到预算后在完整梯度累积步骤结束时停止，实际为 3,970,388，超出 0.301%。学习率 warmup 和衰减也按累计 token 占预算的比例计算，保证到预算末端完成同一进度的调度。

**解析**：为了容纳足够 token，训练器的 epoch 上限可能设得较大。如果仍按那个上限调度学习率，token 预算先到时，训练可能停在另一条学习率曲线的中段，比较中又混入了优化路径差异。

账本分别统计 processed tokens 和 supervised tokens。本对照匹配的是前者，包含非 padding 的输入与答案；序列长度分布、attention 计算和监督比例仍需另外描述。

**结果**：预算终点权重的测试 Recall@32 为 3.226%（13/403），相对 mixed 非思考的 1.985% 高 1.241 pp，95% 区间 [−0.267, 2.949]。匹配处理量后，mixed 仍未显示直接推荐优势。

**追问**：为什么不用 mixed 完整训练的 6,495,405 token？实际比较使用 selected 权重，预算应对应这个权重已经经历的训练量。完整训练终点和选中检查点是两个位置。

**依据**：[SFT scheduler 与停止条件](../train.py#L29)、[tokenmatched 账本](../reports/training/main_direct_tokenmatched_42_complete.json)、[测试结果](../reports/results_v2/direct_tokenmatched_42_test_recent_in2048_thinkFalse_budgetNone_n64_vllm.json)、[配对差值](../reports/PROJECT_REPORT.md)。

<a id="q11"></a>
### 11｜LoRA 和检查点选择如何设置　P1

**面试官**：为什么用 LoRA，怎样选模型？

**答**：项目用 LoRA 减少需要更新的参数，rank 16、alpha 32、dropout 0.05，覆盖注意力的 q/k/v/o 和 MLP 的 gate/up/down 投影，共 10,092,544 个可训练参数。SFT 使用 BF16、梯度检查点、micro batch 1 和累积 16。常规 direct、mixed 与历史变体每 200 步及结束时，用固定验证子集的 non-thinking Recall@32 选权重，同分保留较早检查点；token 匹配变体使用预算终点权重。

**解析**：固定监测样本、生成次数和模式，减少模型选择过程中的口径变化。SFT 的共同监测指标是非思考模式；RL 监测则使用固定验证样本的思考模式，每 100 步评估，两者应分别说明。

rank 16 是本次固定配置，项目没有开展 rank 搜索。要讨论它与 rank 8/32 的取舍，应同时比较训练显存、适配容量和验证表现。

**追问**：为什么训练时关 KV cache？训练需要对完整序列反向传播，配合梯度检查点时关闭 cache；自回归生成再按后端使用缓存。

**依据**：[config](../config.json)、[load_model](../model.py#L20)、[monitor_rl](../train.py#L379)。

## 三、评测与奖励

<a id="q12"></a>
### 12｜Recall@32 是取 32 个不同合法商品吗　P0

**面试官**：无效输出和重复输出怎么计分？

**答**：主评测按原始顺序生成 64 次，Recall@32 用前 32 次尝试。无效答案占一次，重复 SID 也占一次，命中集合才去重。这样每个模型有相同次数的机会，无需为了凑满合法答案追加采样。

**解析**：例如前四次是 `[A, A, 无效, B]`，目标为 B，则 Pass@2=0、Pass@4=1。先去重和剔除无效再说“前两个答案”会把 B 提前，改变预算。

补充实验中的“等有效预算”是另一分析：从已保存输出中提取合法尝试，在共同合格子集比较；它不能替代主评测的固定原始次数。

**追问**：重复率高一定更差吗？重复减少覆盖，但也可能反映集中在高概率候选；应同时看命中、有效率和不同 SID 数。

**依据**：[metrics](../evaluate.py#L10)、[固定次数测试](../tests/test_pipeline.py)。

<a id="q13"></a>
### 13｜这里的 Pass@K 和 Recall@K 为什么相同　P0

**面试官**：它和代码生成里常见的 pass@k 估计一样吗？

**答**：本地每条只有一个目标。前 K 次出现该目标，Pass 为 1，Recall 也为 1；否则都为 0，平均后自然相同。代码计算的是原始前 K 次尝试的经验命中，不使用从 n 个样本和 c 次成功推算任意 k 次成功率的组合估计器。

**解析**：一般多目标情形，`Recall@K = 命中目标数 / 目标总数`，`Pass@K = 是否至少命中一个目标`。例如三个目标命中一个，Recall=1/3、Pass=1。官方任务存在多目标，因此分开报告。

这里的 K 也没有表示学习到的排序前 K。主评测按采样产生顺序截取，项目没有据此计算 NDCG。

**追问**：能把 64 次样本用组合公式估计 pass@32 吗？那将换一个统计量；要采用时需重新统一所有对照，不能与当前前 32 次经验命中混写。

**依据**：[metrics](../evaluate.py#L10)、[官方指标协议](../artifacts/official_execution_protocol_42.json)。

<a id="q14"></a>
### 14｜配对 bootstrap 为什么按组抽样　P1

**面试官**：置信区间怎么算？直接对两组均值分别抽样可以吗？

**答**：先按 sample_id 对齐两个模型，计算每条差值，再把同一个 group_id 的记录放在一起。每次有放回抽取这些组，计算抽中记录的总体平均差，重复 1,000 次，取 2.5% 和 97.5% 分位点。这样既保留同题配对，也保留重复历史内部的相关性。

**解析**：实现保存每组的差值总和与记录数，重采样后用 `总差值 / 总记录数`，所以点估计仍是按记录平均。一个含三条记录的组被抽中时，这三条一起进入该次估计。

对两模型独立抽样会丢失同一题上结果的对应关系；把同组记录独立抽样则会高估独立信息量。

**追问**：区间覆盖训练随机性吗？当前区间来自给定权重与评测样本；训练 seed 变化需要独立训练对照，五个采样 offset 也只增加生成层面的检查。

**依据**：[paired_bootstrap](../evaluate.py#L45)、[配对结果](../reports/final_paired_comparisons.json)。

<a id="q15"></a>
### 15｜全零奖励组为什么学不到命中奖励　P0

**面试官**：GRPO 不是每步都能更新吗？

**答**：GRPO 看同一提示的组内相对奖励。全零时，每个奖励减组均值都为零，任务优势为零。若 KL 正则存在，参数仍可能因 KL 更新，但没有来自本组命中奖励的方向。项目因此先检查奖励标准差非零的组占多少。

**解析**：用四个奖励 `[0, 0, 0, 1]` 手算，总体均值 0.25，标准差约 0.433，标准化优势约 `[-0.577, -0.577, -0.577, 1.732]`。四个全零则全部为零。项目 N×K 实现分母另加 `1e-4`，避免数值除零。

有效组比例的分母是提示组，不是答案条数；精确命中率的分母则是所有尝试。这两个指标分别衡量训练信号覆盖与输出成功概率。

**追问**：全对组呢？奖励同样恒定，任务优势也为零；组内比较需要差异。

**依据**：[branch_advantages](../train.py#L152)、[reward_diagnostics](../train.py#L326)。

<a id="q16"></a>
### 16｜为什么先做 256 条奖励探针　P0

**面试官**：为什么不先跑完 RL 看效果？

**答**：训练探针先回答奖励是否可用。项目在最多 256 个训练提示上检查有效奖励组、精确命中、无效率、前缀命中、截断和目标目录覆盖；有效组不足 1% 时记录诊断并跳过训练。四个正式变体都达到了门槛。

**解析**：低奖励覆盖可能来自真正的任务困难，也可能来自格式解析、SID 特殊 token 丢失、答案截断或目录不完整。先排查后者，避免用“任务太难”掩盖实现问题。

门槛依据训练集设定，测试成绩不参与决定某变体是否训练。多样性分支 `nk_prefix_div` 有探针但不在默认正式队列，这一点与训练完成状态分开记录。

**追问**：22.66% 说明模型提升了吗？这是起始模型输出上的奖励诊断，说明前缀评分能区分更多组；参数更新后的收益由验证和测试测量。

**依据**：[probe_rewards](../train.py#L354)、[探针汇总](../reports/rl/main_probe_summary_42.json)。

<a id="q17"></a>
### 17｜N×K=4×8 和直接采 32 条有什么区别　P0

**面试官**：最终不都是 32 个答案吗？

**答**：GRPO-32 为每个答案生成独立完整轨迹；N×K 先生成四段推理，每段推理接八个答案。它把探索分成“不同推理方向”和“同一推理下不同终局”两层，共享推理可以减少重复生成，并允许对子答案和共享前缀分别分配信用。

**解析**：设推理长度为 Lr、答案长度为 La，生成长度的近似量分别是 `32(Lr+La)` 与 `4Lr+32La`。这是帮助理解结构的计数；实际 token、缓存开销和后端耗时需要读日志。

共享同一推理的答案具有条件相关性，因此 32 个终局也不等于 32 条独立完整路径。项目保留 GRPO-32，使终局答案数相同，再观察结构与成本差异。

**追问**：为什么固定 4×8？它是本次协议配置；N/K 比例搜索需要在统一生成或训练成本下比较。

**依据**：[sample_branches](../train.py#L160)、[分支批量采样](../train.py#L170)。

<a id="q18"></a>
### 18｜前缀奖励如何设计，怎样防止模型钻空子　P0

**面试官**：给部分匹配奖励会不会只学到热门一级码？

**答**：奖励先要求最终答案是目录内的合法商品 SID。全码匹配为 1，前两级匹配为 0.5，只匹配第一级为 0.2，其余为 0。训练同时记录精确命中、前缀命中、一级码熵、覆盖率、训练热门码占比和 KL，用这些指标判断模型是否只集中到少数容易得分的前缀。

**解析**：以目标 `(12,34,56)` 为例，合法候选 `(12,34,90)` 得 0.5，`(12,80,7)` 得 0.2，`(8,34,56)` 得 0。即使 `(12,34,90)` 前两级匹配，只要全码不在目录，仍得 0。

奖励层级是本项目的塑形选择。它提高组内差异，但可能偏向代理目标，因此最终使用精确 SID 命中评价，并进一步做 PID 外部评测。

**追问**：为什么不给推理长度或文风奖励？当前目标是推荐命中与成本，没有独立核实长推理更有用；加长度奖励会直接改变优化方向。

**依据**：[reward](../train.py#L143)、[奖励诊断](../train.py#L326)。

## 四、N×K 更新与实现

<a id="q19"></a>
### 19｜共享推理的优势为什么取均值　P0

**面试官**：怎么把 32 个奖励分给 4 段推理？

**答**：先在一个提示的全部 N×K 奖励上计算共同均值和总体标准差，得到每个答案的优势 Aij。每段推理只进入损失一次，使用其 K 个答案优势的平均值；答案片段分别使用 Aij。这样推理得到的是它能导向怎样一组终局的信用。

**解析**：用 2×2 示例 `[[1,0],[0,0]]`，所有答案的优势约为 `[[1.732,−0.577],[−0.577,−0.577]]`。两段推理的优势分别约 0.577 与 −0.577。第一段有一次成功，第二段全部失败，因此得到不同方向。

如果按每个分支独立标准化，分支之间的整体质量关系被抹掉；如果把共享推理复制 K 遍，在当前 token 归一化方案里会改变推理相对答案的权重。

**追问**：这是否等价于完整 32 轨迹的 GRPO？共享片段计数与损失归一化不同，应把它作为明确的实现选择，再用同终局数对照评估。

**依据**：[branch_advantages / branch_segments](../train.py#L152)、[两提示手算测试](../tests/test_pipeline.py)。

<a id="q20"></a>
### 20｜为什么强制插入的 think 边界不计算生成损失　P1

**面试官**：为什么把推理和答案拆成多个片段训练？

**答**：程序采样推理前缀，接上 `</think>` 和换行，再从这个前缀生成答案。推理片段在原 prompt 后受监督，答案片段以带边界的 branch prompt 为条件受监督。强制插入的边界是程序动作，因此只作为上下文，不当作策略采样出来的 token 更新。

**解析**：答案的条件里包含推理和边界，这些内容参与前向；损失只对该片段的实际 completion 取 log-prob。训练的 token 分母是各生成片段长度之和，共享推理只累计一次。

区分生成 token 与程序插入 token 也用于成本账本：边界不会增加模型生成量，但模型真实生成的推理全部计费。

**追问**：提示词也算进 RL loss 会怎样？会给策略没有采样的输入文本附加优化目标，损失含义随之改变。

**依据**：[sample_branches](../train.py#L160)、[branch_segments](../train.py#L188)、[branched_update](../train.py#L393)。

<a id="q21"></a>
### 21｜policy、old policy、reference 怎样区分　P0

**面试官**：为什么关闭 LoRA 不能作为这里的 reference？

**答**：policy 是正在更新的策略；old log-prob 是计算概率比时使用的固定比较值；reference 是 KL 约束所参照的冻结起始策略。本项目从 mixed-SFT 继续训练，所以 reference 应保留 mixed 的 LoRA。关闭 LoRA 会回到预训练基座，约束对象就变了。

**解析**：标准 GRPO 显式加载冻结 SFT 模型作为 `trainer.ref_model`。N×K 给同一基座加载名为 `reference` 的适配器，并逐张量检查初始权重与 policy 相同。适配器初始化过程还可能经历 BF16 转换，所以实现会在 dtype 提升后重新复制策略权重，保证参考数值一致。

N×K 的 old log-prob 在当前更新开始前由 Transformers 重新计算并 detach；每个提示只做一次 optimizer step。它没有保存 vLLM 采样时每个 token 的行为策略概率，第 23 题继续解释这一点。

**追问**：reference 要随策略更新吗？当前设计冻结为起始 SFT。更新 reference 会把 KL 的锚点变成另一种算法配置，需要重新定义和比较。

**依据**：[load_reference_adapter](../train.py#L426)、[standard_grpo](../train.py#L508)。

<a id="q22"></a>
### 22｜clip 和 KL 分别约束什么　P1

**面试官**：把损失解释到公式，正负优势都怎样工作？

**答**：令概率比 `r = exp(logp_current − logp_old)`，任务项取 `min(rA, clip(r,1−ε,1+ε)A)`。正优势鼓励增大已采样 token 的概率，负优势鼓励降低；clip 限制相对 old 的更新激励。KL 项则约束策略偏离冻结 SFT 参考的程度，项目设 ε=0.2、β=0.02。

**解析**：正优势时，r 超过 1.2 后 clipped 项限制继续提高的激励；负优势时，要结合 min 和 A 的负号理解下界侧的作用，不能只记“把比例裁到区间”。

实现令 `δ = logp_ref − logp_current`，计算 `exp(δ) − δ − 1` 的逐 token KL 代理项。最终把负任务目标与 β 倍 KL 相加，再按生成片段总 token 数归一化。

**追问**：clip 等于 KL 吗？前者相对 old 限制本轮变化的激励，后者相对 reference 保持长期锚点；参照对象和作用都不同。

**依据**：[branched_update](../train.py#L393)、[参数](../config.json)。

<a id="q23"></a>
### 23｜这份 N×K 实现里 clip 实际起多大作用　P1

**面试官**：每组只更新一次，old 和 current 来自相同参数时，概率比是多少？

**答**：按当前实现，old 是在更新前重新算出的 detached log-prob，current 在相同权重下计算，这个 step 的初始概率比接近 1。loss.backward 累积各片段梯度，最后才调用一次 optimizer.step。因此 clip 公式存在，但当前单次更新流程没有多轮复用 rollout 后那种明显的概率比偏离。

**解析**：这里需要把“实现了 clipped objective”和“clip 在实验里实际限制了多少更新”分开。r 的初值为 1，仍有对 current log-prob 的梯度；它不意味着任务项没有学习信号。全零优势组则主要剩下 KL 项。

rollout 用 vLLM，log-prob 用 Transformers，温度都按 0.8 处理，但没有额外的跨后端重要性修正。若改成一组 rollout 多次更新，应保存真实 old 值、监测 ratio/clip fraction，并重新检验训练稳定性。

**追问**：这说明 N×K 必然错误吗？它说明本项目的有效更新方式与多 epoch PPO 不同。解释算法时应对照实际数据流和 optimizer 时机。

**依据**：[branched_update](../train.py#L393)、[方法记录](../reports/method.md)。

<a id="q24"></a>
### 24｜四种 RL 对照分别排查什么　P0

**面试官**：为什么既有 GRPO-8 又有 GRPO-32，还要无前缀 N×K？

**答**：GRPO-8 给出基础精确奖励参照；GRPO-32 检查增加终局采样数；N×K 在同样 32 个终局下引入共享推理；N×K＋前缀在相同分支结构上改奖励。四组从同一 mixed-SFT 出发，使用共同的 500 个训练输入顺序。

**解析**：thinking Recall@32 分别是 2.481%、2.730%、2.730%、4.467%。结合奖励探针，结果把后续分析引向分级反馈。该序列同时保留了没有明显收益的控制组，便于检查“只是采样更多”的解释。

标准 GRPO 使用 Transformers 生成，N×K 用 vLLM 生成；两种训练的损失归一化与共享片段权重也不同。同终局数控制了答案数量，生成 token 与实现差异另外记录。

**追问**：怎样更严格隔离分支结构？后续可以统一采样后端、损失归一化和总 token 预算，只改独立完整轨迹与共享前缀的组织方式。

**依据**：[输入顺序](../artifacts/rl_prompt_schedule_main_42.json)、[主报告](../reports/PROJECT_REPORT.md)。

## 五、成本、路由与历史

<a id="q25"></a>
### 25｜为什么思考预算不是一个 max_new_tokens 就能解释　P0

**面试官**：主对照的 thinking 和 budget=1024 是同一个设置吗？

**答**：主对照 `budget=None` 使用一次自然生成，thinking 的总上限为 1,024 token。预算实验则先给思考段单独设置 128/256/512/1024 上限，遇到结束标记或到预算后，再接最终答案生成，答案最多 32 token。两者的生成阶段和随机数消耗不同。

**解析**：强制预算路径把“想多久”和“有没有机会输出答案”拆开。自然生成可能在总长度内一直没有正确闭合思考；强制边界会让答案阶段继续执行。强制插入的 `</think>` 不计为模型生成 token。

预算为 0 时使用直接回答。报告同时保留推理 token、总生成 token、强制闭合和无效原因，帮助解释分数变化。

**追问**：为什么两张表里同叫非思考，数值还可能不同？主对照生成 64 次，预算实验生成 32 次，路由又由 8＋24 次合并；应按同一采样协议配对。

**依据**：[Generator.generate](../model.py)、[预算实验](../evaluate.py#L226)。

<a id="q26"></a>
### 26｜能否说思考预算减半，成本就减半　P1

**面试官**：512 与 1024 的成本收益怎么表述？

**答**：应读实际生成量。RL prefix 在这两档的 Recall@32 都是 3.722%，token/输入分别为 16,523.2 和 24,635.3，512 档实际减少约 32.93%。上限减半并不意味着实际思考长度或总成本减半。

**解析**：模型可以在上限前自然结束；答案 token 也需要加入。输入 prefill、缓存、硬件占用影响耗时，所以生成 token 主要衡量解码工作量，不直接等于端到端延迟或账单金额。

本项目不同阶段使用共享 4090 和 5090，耗时保留为运行诊断。若要测吞吐或延迟，下一轮应固定硬件、并发、batch、输入长度和预热条件。

**追问**：那默认选 512 吗？路由使用的 256 来自验证集选择；测试上的 512/1024 比较用于解释这次成本曲线，不能回头改已冻结的选择规则。

**依据**：[RL 思考预算汇总](../reports/main_rl_nk_prefix_thinking_42_test_summary.json)。

<a id="q27"></a>
### 27｜八次探测怎样变成自适应路由　P0

**面试官**：路由信号怎么算，测试时怎样确定阈值？

**答**：先生成八次直接答案。uncertainty 信号是合法答案中不同一级 SID 的数量除以 8；另一个信号是原始历史事件数。验证集选出正思考预算中的最佳档位，再按信号与稳定哈希排序，冻结名义 25%/50% 的阈值。测试应用这些阈值，随机对照选相同实际人数。

**解析**：一级码分散度是简单代理，并非校准的模型熵。无效答案不进入不同一级码集合，分母仍是 8，所以信号也受合法率影响。固定阈值意味着测试实际思考比例可以偏离名义比例。

未思考输入复用八次探测并补 24 次；思考输入用 32 个思考答案作为最终集合，八次探测只计成本。重放共享真实调用，保证对照间能配对。

**追问**：为什么随机对照匹配实际人数？否则测试分布变化造成思考人数不同，路由效果就混入预算差异。

**依据**：[thinking_experiments](../evaluate.py#L226)、[冻结阈值](../artifacts/thinking_selection_main_rl_nk_prefix_42.json)。

<a id="q28"></a>
### 28｜比随机路由好，为什么还不说明路由划算　P0

**面试官**：你实现了自适应思考，效果到底怎么样？

**答**：比较有两个问题：同样分配一些思考机会，信号是否比随机挑人更好；整个方案是否比全部直接回答更好。RL 路由相对随机的一些差值为正，但同源全非思考 8＋24 次对照为 4.963%，各路由是 4.467% 或 4.963%，还增加了思考 token，因此本次结果支持保留直接回答作为成本参照。

**解析**：如果只拿随机路由作基线，可能只证明“挑人稍好”，没有证明增加思考本身有价值。探测开销也必须入账，尤其是被丢弃的八个直接答案。

单次 budget 0 的 2.978% 来自另一组调用，不能拿它替代 4.963% 这组与路由共享预测的全非思考基线。

**追问**：还值得研究路由吗？可以先诊断哪些输入在配对结果中确实从思考受益，再在独立验证集设计信号；已有历史长度和分散度的结果为下一轮提供了起点。

**依据**：[路由汇总与配对差值](../reports/main_rl_nk_prefix_thinking_42_test_summary.json)。

<a id="q29"></a>
### 29｜三种历史策略具体怎么选事件　P1

**面试官**：recent、domain_recent、balanced 有什么区别？

**答**：recent 从输入列表尾部优先保留；domain_recent 先给商品事件约一半可用预算，再用尾部事件填满；balanced 先给尾部约一半、补商品到约四分之三，再补未覆盖的领域与一级码组合，最后继续填充。每次都按 tokenizer 检查完整 prompt 的成本，保留完整 SID 事件，输出恢复原始顺序。

**解析**：预算先扣除固定模板与非事件文本。代码用累计 ceiling 控制填充，比例是预算分配策略，不保证每类最终严格占固定 token 比例；某类事件不足时仍继续填充其它候选。

`recent` 在当前数据里表示输入列表尾部。公开样本的 timestamp 为空，所以这项命名对应呈现顺序，时间含义需要有时间戳的数据验证。

**追问**：为什么不按字符串长度裁剪？SID 和模板的 tokenizer 成本才与模型长度限制一致；字符数量不能可靠代表 token 数。

**依据**：[select_history](../history.py#L26)、[render_user](../history.py#L6)。

<a id="q30"></a>
### 30｜历史选择为什么做 2×2 交叉对照　P1

**面试官**：只在评测时把 recent 换成 balanced 不行吗？

**答**：那只能测输入替换，还混着训练与评测分布不一致的问题。项目在同一个 1,024 token 预算和公共训练子集上，分别训练 recent 与 balanced，再各自用两种策略评测，得到四个组合。

**解析**：选择 1,024 是因为至少 30% 的测试输入需要裁剪；实际为 34.243%，2,048 下为零。如果所有历史都装得下，策略实验就没有形成真正的输入差异。

公共训练子集要求两种策略都保留 CoT 引用，避免 balanced 训练集与 recent 训练集不同。两行结果相同：recent 评测 1.489%，balanced 1.985%，差值区间跨零。

**追问**：长度门槛使用 test 是否等于按 test 选最佳策略？当前门槛使用输入长度分布，不读取目标命中率；若研究目标是完全未接触测试输入的新部署，应在独立开发数据上预先冻结长度规则。

**依据**：[history_gate](../history.py#L64)、[历史配对训练](../train.py#L29)、[主报告](../reports/PROJECT_REPORT.md)。

## 六、补充评测与简历压力题

<a id="q31"></a>
### 31｜五次采样到底验证了哪种稳定性　P0

**面试官**：你说五次都提升，是五个训练种子吗？

**答**：是固定 seed 42 权重的五个生成采样 offset。mixed 和 RL prefix 都用同一测试集和非思考协议，五次配对差值全部为正。平均 Recall@32 从 1.836% 到 3.474%，合并差值 1.638 个百分点，分组 bootstrap 区间为 [0.500, 3.027]。

**解析**：先对每条样本的五次命中取均值，再按输入组重采样；没有把 403×5 当作互相独立的 2,015 个用户。训练随机性与生成随机性处在不同层级。

新增 offset 在 5090、原 offset 0 在 4090，本轮波动还包含设备差异。这里的证据集中在固定权重非思考模式；thinking 多采样和训练 seed 43/44 是独立的后续实验。

**追问**：怎样验证训练稳定性？冻结数据、选择和评测规则，为每个训练种子从 SFT/RL 重新训练并选权重，再比较跨训练运行的差值。

**依据**：[eval_seed_summary](../reports/checks/eval_seed_summary.json)、[补充报告 M2](../reports/checks/CHECKS_REPORT.md)。

<a id="q32"></a>
### 32｜召回上涨是不是因为少生成了不存在的商品　P0

**面试官**：模型只是格式更好了吗？

**答**：最主要的无效项是目录外 SID，它们通常格式正确。五次非思考采样中，mixed 与 RL prefix 的平均有效率从 61.163% 到 70.125%。为继续区分有效性与选择，项目在共同拥有至少 16 个合法答案的 393 条输入上比较前 16 个有效尝试，差值为 +0.560 pp，区间跨零。

**解析**：目录成员资格与语法合规是两种检查。模型拼出三层都合法的码，也可能落到不存在的组合。合法率提高会在固定原始次数下增加可用机会。

thinking 的单次分析在 396 条共同合格输入上，等有效预算差值仍为 +1.768 pp [0.253, 3.535]。这使两种模式的诊断更具体：非思考的目录有效性变化最明确，思考还保留有效候选内的命中改善。M1 的这两个区间按 sample_id 做 1,000 次配对 bootstrap；主模型对照与 M2 的重采样单位则是输入组。

**追问**：怎样进一步检查有效性因素？让两模型在同样的目录约束解码下重新评测，并同时记录精确命中与成本；这会形成一个新的实验协议。

**依据**：[有效性分解](../reports/checks/validity_decomposition.json)、[M1 报告](../reports/checks/CHECKS_REPORT.md)。

<a id="q33"></a>
### 33｜等有效预算分析有什么选择效应　P1

**面试官**：把无效输出去掉后比较，是不是更公平？

**答**：它让双方在相同合法尝试数下比较，但只适用于双方都生成了足够合法答案的共同样本。非思考五次采样取共同合格交集 393/403，思考单次为 396/403。它回答条件子集上的问题，与全量固定次数主评测互补。

**解析**：排除的样本可能本身更难，或更容易产生目录外输出。若只报告该子集的高分，读者会误以为它代表所有输入。项目同时保留合格数、排除数、有效尝试命中率和全量主指标。

提取的是按原顺序排列的合法尝试，重复合法 SID 仍占预算；等“不同合法商品数”会是另一个分析。算法也没有额外调用模型补齐 16 个答案。

**追问**：能算合法率贡献了总提升的百分之几吗？这些条件指标不能直接组成因果加法分解；需要额外干预或更明确的统计模型。

**依据**：[decompose](../ops/checks.py#L199)、[补充报告](../reports/checks/CHECKS_REPORT.md)。

<a id="q34"></a>
### 34｜官方 SID 与 PID 结果为什么差这么多　P0

**面试官**：SID Recall@64 7.488%，为什么 PID 只有 2.002%？

**答**：SID 是三级编码，PID 是实际商品标识，一个 SID 可以映射到多个商品。官方协议用 `max_pid` 从映射中选 PID，命中目标 SID 未必命中目标 PID。官方还有多目标标签，因此 SID/PID 与 Pass/Recall 都分别计算。

**解析**：本地独立商品表里有约 208 万个碰撞 SID。这个审计说明编码级目标与商品级目标之间确有一层映射问题；具体分差还受官方标签集合和候选排序影响。

兼容性检查另发现 3 条官方样本的 answer_pid 含有答案 SID 映射未覆盖的商品，评测保留原始标签和全量 1,000 条，记录差异供解释。

**追问**：为什么不用一个碰撞 SID 返回所有 PID？这会改变候选数和官方映射策略；本轮沿用官方协议，若改映射，应另开对照并明确预算。

**依据**：[官方协议](../artifacts/official_execution_protocol_42.json)、[兼容性记录](../artifacts/official_compatibility.json)、[目录审计](../reports/catalog_report.json)。

<a id="q35"></a>
### 35｜“提升 2.233 个百分点”到底比较了谁　P0

**面试官**：这句话能直接写成比直接 SFT 更好吗？

**答**：2.233 pp 比较的是 mixed thinking 的 9/403 与 RL prefix thinking 的 18/403，区间为 [0.478, 4.082]。direct SFT 是 11/403，即 2.730%；相对 direct 的差值是 1.737 pp，区间 [−0.005, 3.528]。介绍结果时要随比较对象一起给出数字。

**解析**：403 条里一个命中约为 0.248 pp，主比较多命中了九条。2.233% 到 4.467% 的相对变化约为 100%，但用命中数和百分点更容易看出实际规模。

样本级配对区间利用了哪些题改善、哪些题退化的信息；两个均值相减只能给点估计，不能代替配对区间。

**追问**：既然 direct 分数更高，为何 RL 从 mixed 开始？mixed 提供直接与思考两种生成路径，便于研究推理分支训练；direct 是需要同时保留的任务效果基线。

**依据**：[最终配对差](../reports/final_paired_comparisons.json)、[RL 对 direct](../reports/nk_prefix_vs_direct_42.json)。

<a id="q36"></a>
### 36｜SASRec 和热门基线都是零，说明了什么　P0

**面试官**：是不是用很弱的基线衬托大模型？

**答**：这两组结果主要揭示当前数据的训练支持。403 个测试目标中，只有 3 条曾作为训练目标，353 条在训练目标和历史里均未出现。模型需要在约 1,030 万个 SID 中检索，传统基线又没有文本或 SID 预训练，因此其零命中要结合这种覆盖结构解释。

**解析**：热门基线只按训练目标频次；SASRec 使用两层因果 Transformer 和 next-target 正负样本监督，最大 200 个事件。评测确实产生了目录内候选，审计将“没有命中”和“没有有效输出”分开。

更有解释力的主对照是相同预训练基础上的 direct、mixed 与 RL。若研究传统序列推荐对比，应补更充分的交互训练、相同预训练支持或合适的 warm/cold 分层协议。

**追问**：它是不是标准 SASRec 全训练配方？这里监督每条记录的最终目标；对每个历史位置做 next-item 监督是另一种训练设置，需要分别说明。

**依据**：[baseline_support_audit](../reports/baseline_support_audit.json)、[baselines.py](../baselines.py)。

<a id="q37"></a>
### 37｜官方任务是否验证了外部提升　P0

**面试官**：外部任务已经做了，最稳妥的结论是什么？

**答**：完整 1,000 条官方商品任务中，mixed 与 RL prefix 的 PID Recall@64 是 1.816% 和 2.002%，差值 +0.186 pp，区间 [−0.275, 0.672]；方向为正，当前样本下区间跨零。SID Recall@64 也呈正向差值，但目录有效率从 17.373% 降到 16.297%。

**解析**：这组对照复用官方 v3.1-public 数据、prompt、Race 32＋32、beam search 和映射评分。RL 模型由本地验证集选出，外部分数不参与选择。mixed 基线补齐后，外部结果可以真正比较两组后训练权重。

本地单目标 SID、官方多目标 PID，以及自然采样和官方 beam/Race 是不同条件。因此外部实验既检查迁移方向，也揭示本地有效性收益没有原样迁移。

**追问**：有了 1,000 条为何还跨零？显著性取决于差值、命中数量、配对分布和变异；样本多于本地并不保证能检出较小的差异。

**依据**：[official_baselines](../reports/checks/official_baselines.json)、[M3 报告](../reports/checks/CHECKS_REPORT.md)。

<a id="q38"></a>
### 38｜有 CoT 就有可解释性吗　P1

**面试官**：你展示的推理是否真实反映了用户行为？

**答**：项目把推荐命中和推理依据分开检查。六个验证案例中，出现输入没有提供的日期、搜索记录以及历史 SID 引用；其中也有最终推荐命中的案例。精确和前缀奖励只核查最终商品编码，推理正文的事实忠实性需要独立评价。

**解析**：引用的 SID 在历史中，只能支持“存在这个行为编码”，不能支持模型添加的日期或搜索动作。反过来，匿名 SID 可能已在预训练中关联到商品语义，因此也不能仅凭输入没有商品名称，就把所有品类分析判为错误。

当前案例检查是定性诊断，不将六个案例外推成全量幻觉率。若下一步研究解释质量，可先标注可核对事实，再做忠实性与命中率的联合评估。

**追问**：这会否定 CoT 的任务价值吗？推理文本是否帮助生成正确目标，与文本每项事实是否成立，是两个都值得测量的问题。

**依据**：[case_review](../reports/case_review.md)、[输入来源回查](../reports/case_input_origin_audit.json)。

## 七、工程与下一步

<a id="q39"></a>
### 39｜实验中断后，怎样保证续跑结果还能比较　P1

**面试官**：文件还在就接着运行吗？如果模型或 prompt 换了呢？

**答**：预测文件配有 settings，记录适配器哈希、seed、采样 offset、模式、预算、后端、协议与运行标识。续跑先比较设置，再跳过完成的 sample_id；缓存复用还核对样本和实际 prompt 哈希。训练保存模型、优化器和随机状态，主队列用锁避免重复运行，子任务失败就停止。

**解析**：路径相同不代表权重相同，输入策略名字不同也不代表最终 prompt 一定不同，所以复用依据是模型与采样身份、样本身份和实际文本。N×K 每步加载当前 LoRA，更新期间让 vLLM 休眠，防止 rollout 使用旧适配器。

官方批次缓存只保存完整输出，失败批次重跑；v2 评测与旧版输出分目录，避免混入旧后端结果。v2 贪心检查 29/32 一致，因此正式模型比较统一后端。

**追问**：本地 CPU 测试验证了什么？解析、分组、信用分配、预算、缓存与统计逻辑；GPU 数值、权重加载和完整训练仍使用对应环境的实验记录。

**依据**：[evaluate_one / cache](../evaluate.py#L70)、[pipeline](../run.py#L81)、[official_cache](../ops/official_cache.py)、[后端检查](../reports/backend_parity_v2.json)。

<a id="q40"></a>
### 40｜再给一周算力，你先做什么　P0

**面试官**：下一步不能只说扩数据、换大模型，具体怎么决定？

**答**：我会先围绕现有结果做两步。第一步，在相同目录约束解码下比较 mixed 与 RL prefix，观察非思考收益在合法率接近后还剩多少；第二步，冻结当前数据与选择规则，补独立训练种子，检查前缀奖励的差值能否跨训练运行保持方向。两步分别检验收益机制和训练稳定性。

**解析**：每个实验都应事先写出会怎样改变判断。若约束解码后差值明显收缩，就优先把目录有效性作为工程收益，并比较约束解码与 RL 的成本；若差值仍存在，再分析有效候选排序和覆盖。若跨训练种子波动大，就检查奖励覆盖、目标分布和模型选择，而不是只报告最好的一次。

若岗位更关注部署，可以把第二步换成固定硬件上的成本评测，测 prefill、decode、P50/P95 延迟与吞吐；若关注推荐研究，则补用户/时间划分和更强基线。新的方案用独立评测集验证，当前结果负责提出假设。

**追问**：项目最有价值的工作怎么概括？把可运行的 SFT/RL 接成可解释的实验：数据和预算有明确定义，奖励覆盖能检查，最终结果能分解，并能回到源文件与调用记录。

**依据**：[当前结果与条件](实验结果与来源.md)、[补充评测](../reports/checks/CHECKS_REPORT.md)。
